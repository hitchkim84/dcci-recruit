# 보안 구조와 잔여 위험

## 1. 접근 통제 (세 겹)
1. **화면**: 등급에 맞는 메뉴만 보인다(편의 기능일 뿐 보안 장치로 보지 않는다).
2. **서버**(`netlify/functions`): 모든 요청에서 Supabase Auth로 토큰을 확인하고, 등급(`app_metadata.role`)·OTP(`aal2`)·로그인 방식(`amr`)을 검사한다. 입력값은 `public/js/rules.js`로 검증한다.
3. **DB**(`sql/`): 모든 표에 RLS + 정책 없음 + 권한 회수 → 표 직접 읽기·쓰기 불가. DB 함수가 `auth.uid()`로 본인 데이터만 다루고, 관리자 함수는 등급·OTP·지정 공고를 다시 확인한다. 서버 전용 함수는 service_role만 실행.

| 대상 | 규칙 |
|---|---|
| 지원자 | 이메일 일회용 코드 인증 후 **본인 지원서만**(`auth.uid()` 일치). 관리자 계정은 지원 기능 사용 불가 |
| 슈퍼관리자 | `role=admin` + **aal2(OTP 통과)**. OTP 없는 로그인은 서버·DB 모두 거절 |
| 일반 담당자 | `role=staff` + **비밀번호 로그인(amr=password)** + `posting_staff`에 지정된 공고만 조회·다운로드. 수정·삭제·계정·설정 함수는 서버와 DB에서 거절 |
| 공개 | 공개 조회 함수 3개(게시·마감 공고, 게시된 공지·FAQ·문의처)만. 개인정보 없음 |

## 2. 항목별 대책
| 요구 | 구현 |
|---|---|
| 불필요한 민감정보 미수집 | 주민등록번호·가족관계·성별 항목 없음. 증명사진은 공고별 선택(기본 꺼짐, 채용절차법 제4조의3 검토 필요). 생년월일·주소·병역은 공고별 선택. 알 수 없는 입력 항목은 DB가 버린다 |
| 수집 항목·동의문·보유기간 설정 | 공고별 지원서 항목·동의문·보관기한. 미확정 문구는 `[검토 필요]` 표시. 동의문이 없으면 제출 불가 |
| 마감 판정 | DB 서버 시각 `now()`와 timestamptz 마감 시각 비교(한국 시간 입력값을 +09:00으로 저장) |
| 중복 제출 | 공고당 1인 1건 제약 + 행 잠금 + 같은 내용 재요청은 같은 접수번호 반환 + 화면 버튼 잠금 |
| 첨부파일 | 비공개 버킷, Storage 정책 없음(서버 키만). 업로드는 서버가 권한 확인 후 발급한 서명 업로드 주소(덮어쓰기 불가)로만. 업로드 후 서버가 실제 파일 서명(매직 바이트)·크기 확인, 불일치 시 삭제. 확장자 7종·파일당 최대 10MB·서류당 3개·전체 20개 |
| 다운로드 | 권한 확인·기록 후 **60초** 서명 주소(증명사진 JPG·PNG만 화면 표시용 inline 주소, 나머지는 항상 내려받기). 파일명은 `접수번호_서류구분.확장자`(개인정보·특수문자 없음). 저장 경로도 `지원서ID/첨부ID.확장자` |
| CAPTCHA | Supabase Auth의 Turnstile 검증(인증코드 요청·관리자 로그인). Auth 서버가 검증하므로 화면을 거치지 않은 직접 호출도 막힘 |
| 직접 DB 호출 우회 | 표 권한 없음. 지원자 함수는 로그인(=CAPTCHA 통과 인증) 필요, 같은 검증을 DB에서 다시 함. 첨부 확정·파기·기록 함수는 service_role 전용 |
| 개인정보 노출 경로 | URL에 개인정보 없음(공고 ID만). 서버 로그에는 오류 코드만. 관리자 기록에는 ID·건수만(이름·연락처 미기록). 샘플 데이터는 `[개발용 가상]` |
| XSS | 화면 출력은 모두 `RC.esc()`. 모든 페이지 CSP: 외부 스크립트는 Cloudflare Turnstile만, 인라인 스크립트 금지, 다른 사이트에 끼워 넣기 금지 |
| CSV 수식 삽입 | `= + - @ 탭 CR`로 시작하는 값 앞에 `'` |
| 관리자 활동 기록 | 명단 조회·상세·CSV·첨부 열람·전형 변경·결과 공개·삭제·공고/공지/설정 변경은 DB 함수 안에서, 계정 생성·삭제·비밀번호 변경·수동 파기는 서버에서 기록(기록 실패 시 작업 중단). CSV·첨부는 기록과 데이터 조회가 한 트랜잭션 |
| 파기 | 공고 보관기한 다음 날 매일 03:10 자동: DB 행 삭제 → 파일 경로를 대기 목록에 → Storage 삭제 → 결과 기록. 실패분은 다음 실행 때 재시도. 보관기한 미입력 공고는 파기하지 않음 |
| 비밀값 | service_role/secret 키는 Netlify 서버 함수에서만(Production 범위). SMTP·Turnstile 비밀 키는 Supabase 대시보드에만 |
| 세션 | 브라우저 탭(sessionStorage)에만 저장. 관리자 30분 무조작 시 자동 로그아웃 |

## 3. 잔여 위험 (알고 받아들이거나 추가 조치가 필요한 것)
1. **일반 담당자 OTP 미사용(확정된 운영 조건)**: 담당자 비밀번호가 유출되면 그 담당자에게 지정된 공고의 지원서·첨부파일이 노출될 수 있다. (완화: 개인별 계정, 12자 이상 비밀번호, 지정 공고만 접근, 모든 조회·다운로드 기록, 퇴사 시 즉시 삭제, 월 1회 기록 확인)
2. 이메일 인증은 **메일함 접근 = 본인**으로 본다. 지원자 메일 계정이 탈취되면 그 지원자의 지원서가 노출될 수 있다.
3. 관리자 이메일로 지원자용 인증코드를 요청하면 그 메일함 소유자는 aal1 세션을 얻지만, 관리자 기능은 OTP(슈퍼)·비밀번호 로그인(담당자)을 요구하므로 관리 기능에 접근할 수 없다. 담당자 계정은 메일을 받지 않는 가상 도메인을 쓴다.
4. 업로드 파일의 **바이러스·악성 매크로 검사 없음**(형식 서명만 확인). 담당자는 최신 백신이 설치된 PC에서 열고, HWP·DOCX 매크로를 실행하지 않는다.
5. 내려받은 CSV·첨부·인쇄물은 담당자 PC에 남는다(시스템 밖). 업무 후 삭제 안내가 필요하다.
6. 지원자 회원가입(인증코드 요청)이 열려 있어 가짜 계정이 만들어질 수 있다(로봇 확인·발송 한도로 완화, 계정만으로는 데이터 접근 불가).
7. 결과 공개는 지원자가 직접 확인하는 방식이며, 메일 알림이 없다(향후 과제).
8. **보관기한·기록 보관 일수·동의문·개인정보처리방침은 미확정**: 업무 기준 확정 전에는 자동 파기가 동작하지 않는다(보관기한 비어 있음).
9. 이 저장소는 공개 저장소다. 코드 구조가 공개되므로 비밀값을 절대 커밋하지 않는다(현재 커밋된 비밀값 없음, 로컬 흉내 서버의 개발용 값만 있음).
10. Supabase Free 플랜으로 운영하면 일시 정지·백업 제한 위험이 있다(Pro 권장).
