# 설계 정리: 참고 사이트 확인 결과, 메뉴·화면, DB 구조, 기술 선택

## 1. 참고 사이트 확인 결과 (https://dware.intojob.co.kr/main/korcham.jsp)
- **직접 확인하지 못함.** 개발 환경의 네트워크 정책이 해당 주소를 차단했다(2026-10-02, 접속 거절).
- 공개 검색 결과로 확인한 사실만: 대한상공회의소 채용 접수용 사이트이며, 온라인 입사지원서·자기소개서를 작성해 접수하고, 전형은 서류→필기→면접 순으로 안내된 사례가 있다.
- 메뉴 구성, 공고 목록·상세 화면, 지원 절차 화면, 지원내역 확인 화면은 **확인하지 못했다.** 이 프로젝트의 화면은 일반적인 공공·경제단체 채용 사이트 흐름(공고 목록 → 상세 → 본인 확인 → 작성 → 제출 → 지원내역)으로 설계했다.
- 참고 사이트와 비교해 보완하려면 다음 화면의 캡처만 있으면 된다(개인정보는 가리고): ① 메인(공고 목록) ② 공고 상세 ③ 지원서 작성 첫 화면과 항목 구성 ④ 지원내역 확인 화면.
- 타 기관의 로고·문구·이미지는 사용하지 않았다. 로고는 교육 홈페이지에 있는 대구상공회의소 로고 사본(`public/img/logo.png`)을 사용자 승인 후 사용했다.

## 2. 메뉴·화면
| 화면 | 주소 | 내용 |
|---|---|---|
| 메인 | `/` | 진행 중 공고(카드: 모집 분야·고용형태·접수기간·상태·지원 버튼), 마감 공고, 채용 절차(온라인 지원 순서 + 담당자가 입력한 전형 절차), 공지사항, FAQ. 공고가 없으면 '준비 중' 안내 |
| 공고 상세 | `/posting.html?id=` | 모집 분야·인원·업무, 지원자격, 우대사항, 근무조건, 전형절차, 제출서류, 접수기간, 문의처. **담당자가 입력한 항목만** 표시 |
| 지원서 | `/apply.html?id=` | 이메일 인증 → 기본정보·지원분야·학력·경력·자격·자기소개·첨부(공고 설정에 따라) → 임시저장/다시 작성/미리보기 → 동의 → 최종 제출 → 접수번호 |
| 지원내역 | `/my.html` | 이메일 인증 후 본인 지원서만 공고별로: 제출 상태, 접수번호, 공개된 결과, 수정·취소(공고 설정 시) |
| 관리자 | `/admin.html` | 슈퍼관리자: 채용공고 / 지원자 / 공지·FAQ / 담당자 계정 / 설정 / 기록·파기. 일반 담당자: 지원자(지정 공고) |
| 개인정보처리방침 | `/privacy.html` | 설정에 입력한 확정본. 미입력 시 '검토 필요' 표시 |

## 3. DB 구조 (Supabase PostgreSQL, `sql/01_schema.sql`)
| 표 | 내용 |
|---|---|
| `postings` | 공고. 상태(draft/published/closed/archived), 접수 시작·마감(timestamptz), 모집 분야(jsonb), 안내 문구, 지원서 항목 설정(`form_config`), 수정·취소 허용, 동의문, 보관기한(`retention_until`) |
| `applications` | 지원서(공고당 1인 1건). 상태(draft/submitted), 내용(jsonb), 접수번호, 동의 시각·동의문 해시 |
| `application_reviews` | 전형 단계·내부 메모(담당자 전용), 공개된 결과(`published_stage`) |
| `attachments` | 첨부 메타정보. 파일은 비공개 Storage `applicant-files/지원서ID/첨부ID.확장자` |
| `application_events` | 제출·수정 제출·취소·첨부 변경 기록 |
| `posting_staff` | 일반 담당자 ↔ 지정 공고 |
| `notices`, `faqs`, `site_settings` | 공지·FAQ·사이트 설정(문의처, 방침, 기본 동의문, 기록 보관 일수) |
| `admin_access_log` | 관리자 활동 기록(조회·다운로드·변경·계정 관리) |
| `pending_file_deletes`, `purge_log` | 파일 삭제 대기 목록, 자동 파기 실행 결과 |

모든 표: RLS 켬 + 정책 없음 + anon/authenticated 권한 회수 → 화면은 DB 함수(02~05)로만 접근. 함수가 로그인한 사람·등급·OTP·지정 공고를 확인한다.

## 4. 기술 선택: Netlify + Supabase (채택)
요구 기능과 대조한 결과:
| 요구 | Supabase/Netlify 기능 | 판단 |
|---|---|---|
| 비밀번호 없는 본인 확인 | Supabase Auth 이메일 일회용 코드(OTP) | 적합 |
| 슈퍼관리자 OTP | Supabase Auth TOTP MFA(aal2) | 적합 |
| CAPTCHA 서버 검증·우회 차단 | Supabase Auth CAPTCHA(Turnstile)를 Auth 서버가 검증 → 직접 API 호출도 막힘 | 적합 |
| 다른 지원자 데이터 차단 | PostgreSQL RLS + DB 함수의 auth.uid() 확인 | 적합 |
| 비공개 첨부·짧은 서명 URL | Supabase Storage 비공개 버킷 + signed URL | 적합 |
| 서버 판정(마감·검증), 서버 키 보호 | Netlify Functions | 적합 |
| 자동 파기 | Netlify Scheduled Functions(매일) | 적합 |
| 소규모 운영 | 서버 관리 불필요, 교육 홈페이지와 같은 구조라 담당자가 익숙 | 적합 |

한계: 운영 메일 발송에는 별도 SMTP가 필요(Supabase 기본 메일은 운영용이 아님), Supabase Free 플랜은 장기간 미사용 시 일시 정지·백업 제한, 업로드 파일 바이러스 검사 기능 없음(→ 잔여 위험).

## 5. 초기 버전에서 뺀 것 (향후 과제)
- 지원 접수·결과 공개 시 이메일 알림(현재는 화면의 접수번호·지원내역으로 확인. 추가 시 발송 서비스 비밀값을 서버에 둠)
- 문자(SMS) 인증·알림, 휴대폰 본인확인 서비스
- 블라인드 채용 화면 모드(담당자 화면에서 이름 등 가리기), 평가 점수 입력·합산, 면접 일정 관리
- 첨부파일 바이러스 검사, 지원서 PDF 서버 생성(현재는 브라우저 인쇄 → PDF 저장)
- 취업지원대상자·장애 등 가점 항목(민감정보이므로 법무 검토 후)
- 채용서류 반환 청구 처리 화면(채용절차법 관련, 업무 기준 확정 후)
- 자동 AI 평가·HR 시스템 연동(별도 요청 시)
